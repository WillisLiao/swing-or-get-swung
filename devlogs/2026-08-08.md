# 2026-08-08

## Fifteenth session - performance regression diagnosed and fixed, via `/sonnet-opus`

The user deployed the fourteenth-session build to their iPad and reported it "super laggy."
`handoffs/NEXT-SESSION-performance-regression.md` (written the same day, previous session) ranked three suspects with file:line pointers: the sniper scope picture-in-picture second render pass, the seven autonomous bots recomputing pathfinding every physics tick, and the High Alert chip's per-opponent raycast.
This session measured before changing anything, then fixed the real causes without reverting any of the three systems, per the user's explicit instruction.

**Measurement.**
Confirmed via code inspection that the scope viewport already resets to `UPDATE_DISABLED` when not scoped (`scripts/duelist.gd:589` at the time) - not a bug, a real cost tradeoff.
Confirmed High Alert's raycast is already gated behind cheap early-outs (team, eliminated, ADS threshold, aim cone) that run before the physics query, in the right order.
Used the existing `_arena_perf_sample` harness (`--offline-squad=<n> --arena-perf-sample`, prints avg/min/max frame time over 120 frames) headlessly on desktop: solo (0 bots) and full-squad (7 bots, 8s into the match so bots were actively pathing, not still holding their opening position) both came back flat at the 120fps cap (`avg_ms=8.33`, zero variance).
That is real signal but a limited one - headless mode never touches the GPU at all, so it can only rule bots/High Alert in or out on CPU, and says nothing about the scope viewport's GPU cost by construction.
Given that, and that mobile CPU/GPU headroom is far tighter than this desktop Mac's, the fix took the "make it cheaper, not free" path on both real suspects rather than declaring either innocent from a desktop-only number.

**Fix 1 - sniper scope (`scripts/duelist.gd`).**
The scope viewport still renders the full scene through `nuclear_pbr` a second time while scoped, but no longer every frame.
It now throttles to `SCOPE_REFRESH_SECONDS` (1/30s) via `SubViewport.UPDATE_ONCE` - a documented Godot 4 mode that renders once and reverts to `UPDATE_DISABLED` automatically - instead of running `UPDATE_ALWAYS` at up to 120Hz.
The scope camera's transform and recoil kick still update every frame, so aiming and recoil read the same; only the actual re-render (and its shading cost) is throttled to roughly a quarter of the previous frequency at 120Hz.
Verified live via MCP `game_eval`: forced ADS/sniper on the local duelist, confirmed `render_target_update_mode` cycles `UPDATE_ONCE -> UPDATE_DISABLED` on schedule with `get_texture()` staying valid throughout, and confirmed it still correctly parks at `UPDATE_DISABLED` when not scoped.

**Fix 2 - autonomous bots (`scripts/bot_duelist.gd`).**
`RiftlineMap.route_toward()` (a per-call walk of every route node against every route blocker/solid when the direct line is obstructed) was being called from `_objective_move_input()` every physics tick, for all seven bots, unconditionally.
It is now cached and recomputed on a `ROUTE_RECOMPUTE_SECONDS` (0.2s) interval, jittered per-bot (`+ randf_range(0.0, 0.08)`) so seven bots don't all recompute on the same tick, with an early recompute trigger if the objective goal itself moves more than 3m since the last route decision.
The steering direction is still derived from the cached waypoint every tick, so a bot's movement input is still smooth and responsive - only the expensive "which via-node to route through" decision is throttled, exactly the fix the diagnosis handoff suggested.

**High Alert - left alone.**
Confirmed its early-outs already short-circuit before the raycast in the right order; no measured or structural reason to change it this session.

**Verification.**
Clean Godot 4.7.1 headless import, all 18 `tools/*_exercise.gd` scripts pass (17 existing plus one added since the fourteenth session's writeup), MCP live main-scene launch reports no runtime errors, and the scope-throttle behavior above was inspected live via `game_eval`, not just read from source.
Not verified on the actual iPad this session - that is the same gap that let the regression ship in the first place, and remains explicitly open. The next real signal on whether this is enough should come from a fresh on-device playtest, not another editor pass.

**Going forward:** the user asked that future development stay optimized for mobile CPU/GPU cost as an ongoing discipline, not a one-off cleanup - see the new "Performance discipline" note below and the standing rule added to this file's own conventions.

## Same day, second round - GPU/CPU thermal diagnosis, physics tick cut, sniper scope rebuilt as FOV zoom

On-device testing surfaced two more real problems the first round's frame-time-only measurement couldn't see: the iPad ran hot even when frame time looked "smooth" (a frame that finishes early on a capped GPU still runs at a high, power-hungry clock - frame-time headroom and absolute work per frame are different things), and the sniper scope was still laggy and now looked "chunky, lower resolution" after the first round's AA-disable fix.

**GPU/CPU thermal diagnosis (`opus-advisor`, Medium - crossed rendering/shader/lighting/project-config systems, exactly the "multi-layer causal reasoning already tried and failed" trigger for an Opus consult).**
Found the real always-on costs: full native iPad resolution at up to 120fps through a 16-hash-per-fragment procedural shader (`shaders/nuclear_pbr.gdshader`), 4-cascade real-time shadows using an expensive PCSS-style filter (`light_angular_distance = 0.6`), and a sky radiance cubemap recomputing every frame with no need to.
Fixed all of it: `rendering/scaling_3d/scale = 0.7` (bilinear), shadow cascades 4→2 with a capped max distance, `light_angular_distance = 0.0` (the single best cost-to-visual-loss ratio of the list), sky baked once via `PROCESS_MODE_QUALITY`, and decorative landmark geometry (light strips, storm-ring bars, pad rings - never a route blocker or gameplay-relevant `_build_solids()` collision body) no longer casts shadows.

**Physics tick 120→60Hz with physics interpolation.**
Verified CoD Mobile's own netcode runs at 30Hz - 120Hz local physics simulation was unusually high by shipped-mobile-shooter norms for no measured gameplay benefit.
Cut to 60Hz; added `SceneTree.physics_interpolation = true` so rendering still runs up to 120fps with no judder, and added `reset_physics_interpolation()` at every genuine teleport (`Duelist.respawn_at()`, a hard `reconcile_from_authority()` snap, the nuclear core returning to center) so those still snap instead of smearing.

**A real infrastructure bug found and fixed along the way.**
`project.godot` text edits turned out to be unreliable in this environment - not just a stale in-memory copy (the existing HANDOFF.md warning), but confirmed capable of silently dropping an entire new section outright the next time the Godot editor opens the project, independent of comment formatting.
Burned real time chasing this as if it were a settings bug before isolating it via `git stash` and fresh isolated test projects.
Fix: moved every performance-critical setting (`physics_ticks_per_second`, `physics_interpolation`, `scaling_3d_scale`/`scaling_3d_mode`) into script (`RiftlineArena._ready()`), which is immune to it since it isn't `project.godot` text. Also confirmed a separate, unrelated headless-capture null-texture error is pre-existing on the unmodified `main` baseline (`git stash` test), not a regression from this session. Both findings are now recorded in `handoffs/HANDOFF.md`'s Tooling section.

**Sniper scope rebuilt as main-camera FOV zoom, picture-in-picture removed entirely (`opus-advisor`, Medium, second consult - user explicitly asked for Opus after two of my own fix rounds still hadn't resolved it).**
The prior round's fixes (30Hz render throttle, then disabling MSAA/TAA) didn't fix "still laggy," and the second one caused a real new regression ("chunky, lower resolution").
Opus's diagnosis, verified by direct citation check: the scope picture was drawn at up to 86% of screen height (`duel_hud.gd`'s `_draw_scope_overlay()`, `radius := lerpf(short_edge * 0.95, target, seated)`) from a 512px source texture - a 2.75-4.4x upscale that no AA setting could fix - while the underlying technique (a second full-scene camera render every throttled frame) was never going to be cheap on a tile-based mobile GPU regardless of tuning.
It also caught a real bug in my own first-round HUD redraw-gate fix: the scope texture was pushed to the HUD unconditionally every physics tick (`riftline_arena.gd`), and the redraw gate checked `_scope_texture != null` - true for any local player at all times, sniper or not - silently defeating the entire "only redraw on change" fix for the whole match.
Removed `Duelist._scope_viewport`/`_scope_camera` entirely; the sniper now zooms the main camera's own FOV via `RiftWeapons.ads_horizontal_fov()`, the exact mechanism every other weapon's ADS already used (the sniper was previously excluded from it specifically to make room for the picture-in-picture design).
`duel_hud.gd`'s tube/vignette art is visually unchanged but now masks the whole screen instead of just its own footprint, since the now-real zoomed view fills the entire screen until masked.
Added magnification-aware ADS look-sensitivity scaling, sniper-only (`DuelHud._ads_magnification()`) - the sniper's 3x/6x zoom is far higher than any other weapon's 1.1-1.5x, and player look input never actually reached a zoomed camera under the old picture-in-picture design, so this was never exercised before.
Removed the now-dead `scope_viewport_texture()`/`set_scope_texture()` plumbing.

**Verification.**
Clean headless import, all 18 exercises pass both after the thermal-diagnosis round and again after the scope rebuild.
Live MCP verification: `Engine.physics_ticks_per_second`/`physics_interpolation` confirmed active via the engine's own interpolation warning firing during `game_eval` testing; both sniper zoom stages (3x/6x) screenshotted live via `game_eval` forcing ADS state, confirmed full-screen mask reaching the true screen edges, correct FOV narrowing, and a crisp full-resolution view with no upscaling artifacts - no runtime errors in either the editor or game logs.
Deployed to the iPad four times across both rounds (two blocked mid-deploy by the device locking, both recovered once unlocked).
**Still not verified on-device by the user for this second round as of this entry** - deployed and launched cleanly, but real on-device feedback (thermal + the scope specifically) is the next real signal, same as every prior round.

## Same day, third session - in-game local kill/death totals

The user narrowed the next combat-information feature to the local player's own kill and death counts during play. This session adds exactly that surface, without a kill feed, assists, headshots, or a post-match scoreboard.

**Authoritative rules and LAN replication (`scripts/riftline_match.gd`).**
`RiftlineMatch` now owns a sanitized per-actor combat-stat dictionary and emits `combat_stats_changed` only when the match resets, a valid defeat is recorded, or a replica receives changed totals. Every accepted defeat increments the victim's deaths. A kill is awarded only when the killer is valid, registered, not the victim, and on the opposing team; null/environmental and self deaths never fabricate kills. Totals survive the existing respawn flow and reset in `_start_match()`. `authoritative_state()` carries the totals inside the existing additive `match` snapshot, and `apply_replica_state()` sanitizes them, so LAN clients and reconnecting players display host-owned values without a protocol-breaking input change.

**Arena/HUD integration (`scripts/riftline_arena.gd`, `scripts/duel_hud.gd`).**
Both offline and LAN directors connect the new signal to the local HUD. Local actor assignment/removal and match replacement also resync or clear it, preventing one actor's totals leaking into another session. The HUD draws a compact `KILLS | DEATHS` plate in the top-left safe area, visually separate from the Nuclear Rush objective score so eliminations cannot be mistaken for match points. `set_combat_stats()` clamps invalid negatives and exits without `queue_redraw()` when values have not changed; there is no new continuous redraw or per-frame UI path.

**Verification.**
Godot 4.7.1 headless import is clean and all 18 `tools/*_exercise.gd` scripts pass. `riftline_modes_exercise.gd` now locks kill/death accounting, respawn persistence, environmental-death behavior, LAN replica transfer, and rematch reset; `riftline_combat_hud_loadout_exercise.gd` covers HUD values and sanitization. A windowed MCP main-scene run proved that recording an authoritative host kill changed both `RiftlineMatch.combat_stats_for("host")` and the live HUD from 0 to 1 through the signal path. The 1280x588 gameplay frame was visually inspected with `12 KILLS / 4 DEATHS`: full labels were readable and did not overlap the match strip, squad markers, or mobile controls. Runtime logs contained no project errors; the only warning was the already-known benign physics-interpolation Camera3D warning. The sampled editor run reported roughly 95-99 FPS, 300 draw calls, ~0.085-0.087 ms physics time, and no new per-frame path was added. No phone or iPad was launched or tested, honoring the user's explicit instruction not to open the game on those devices unexpectedly.
