## The seven bugs, verbatim from the user, plus what was found before handoff

### 1. ADS reticle doesn't move with recoil - "seems like it's not on the sight"

**Confirmed, not yet fixed.** The reticle is drawn as a flat 2D HUD overlay, not attached to the 3D sight geometry - this was a deliberate choice from an earlier session (see the comment on `_add_reflex_sight()` in `scripts/duelist.gd`: "The aiming dot is drawn by the HUD at exact screen center... the player looks through a real housing instead of at an opaque emissive disc"). That's optically defensible on its own (real red-dot/holographic sights are parallax-free - the dot doesn't shift on target as your eye moves within the housing), but the *housing* now visibly kicks hard under the new recoil-throw work, and the reticle staying perfectly glued to `size * 0.5` while the housing jumps around it reads as disconnected - which is what the user is describing.

- `scripts/duel_hud.gd:625` - `_draw_gameplay_hud()`: `var center := size * 0.5` then `_draw_reticle(center)` at line 629. `center` never moves.
- `scripts/duel_hud.gd:116-119` - `DuelHud` already mirrors `Duelist.ads_progress`/`zoom_index` into `_ads_progress`/`_zoom_index` each frame (search `_ads_progress =` around line 338) as a precedent for pushing new per-frame state from the Duelist into the HUD the same way.
- `Duelist._recoil_kick` / `_recoil_lateral` (the same two fields driving the 3D throw in `_process()`, around `scripts/duelist.gd:456-470`) are private (`_`-prefixed) and not currently read by anything outside `Duelist`.

**Likely fix shape:** add a small public getter (or a pushed field, matching the `_ads_progress` pattern) exposing enough of the recoil state for `DuelHud` to nudge `center` by a proportional pixel offset in `_draw_ads_reticle()`/`_draw_scope_reticle()` (not the hip reticle, which has its own bloom-driven spread already and isn't what the user is complaining about) - not a full 3D-to-2D projection of the actual dot mesh, that's much more work for a fix whose whole point is "makes the housing's motion visible in the reticle too." Confirm the exact feel with the user or your own judgment on magnitude - don't just wire it at 1:1 scale and assume that reads well; it's a visual-feel call, worth routing through `frontend-opus` or checking against a real screenshot before calling it done.

### 2. Recoil/muzzle-flash "doesn't work all the time" - after class change or death+respawn

**Partially diagnosed, not confirmed as the whole story.** Found one real, confirmed bug:

- `scripts/duelist.gd:552-562`, `set_weapon_presentation()`:
  ```gdscript
  func set_weapon_presentation(next_weapon: Weapon) -> void:
      var clamped := RiftWeapons.clamp_weapon(int(next_weapon)) as Weapon
      if weapon == clamped and _weapon_mesh != null:
          return
      ...
  ```

  This is an existing optimization (skip a full model rebuild if the weapon didn't change) that predates this session. `respawn_at()` (`scripts/duelist.gd:1008-1037`) always calls `set_weapon_presentation(loadout_slots[0])` at the end - and if the respawning weapon is the *same* one the player died holding, this early-returns and **`_rebuild_weapon_models()` never runs on respawn**. Whether this actually causes the "recoil/flash stop working" symptom wasn't confirmed before handoff - `_weapon_rig.position` should self-correct back toward zero within a few frames regardless (it's driven by `_recoil_kick`, which `respawn_at()` does reset to 0, via the lerp in `_process()`), so this alone may not be the full explanation. Worth checking live: force a death mid-recoil-throw (`_weapon_rig.position` non-zero), respawn with the same weapon, and watch whether recoil/muzzle-flash actually resume working on the next shot, or stay dead.
- `configure_loadout()` (class switch, `scripts/duelist.gd` - search `func configure_loadout`) calls `_rebuild_weapon_models()` directly, not through `set_weapon_presentation()`, so it does *not* have the same early-return guard - the "after character changes" part of the bug report needs a different explanation than #2's confirmed cause, not yet found. Don't assume the `set_weapon_presentation` fix covers the class-change case too.
- Check with `is_instance_valid(_muzzle_flare)` / `is_instance_valid(_weapon_rig)` type diagnostics live via `game_eval` rather than re-reading the code again from scratch - this is exactly the kind of intermittent bug that's faster to catch red-handed in the running game than to fully reason out statically.

### 3. Sniper "totally stagnant" under recoil when shooting

**Root cause is understood, not yet fixed, and is very likely a real design gap rather than a bug in the recoil code itself.** `scripts/duelist.gd:423`:
```gdscript
_weapon_rig.visible = weapon != Weapon.SNIPER or ads_progress < SNIPER_SCOPE_HANDOVER
```
Once a scoped-in sniper's `ads_progress` passes `SNIPER_SCOPE_HANDOVER` (`0.42`, `scripts/duelist.gd:88`), the entire first-person weapon rig - which is what carries the recoil throw - is hidden, and the HUD's scope vignette/reticle takes over instead (by design, a physically modeled scope tube can't be looked through in a raster render - this was resolved deliberately in an earlier session, see `devlogs/2026-08-07.md` "Fifth session"). So recoil is very likely still happening mechanically, it's just invisible because the thing throwing is hidden. If the user was testing by scoping in (the normal way to use a sniper), this fully explains "totally stagnant." Confirm hip-fire (unscoped, `ads_progress` low) sniper recoil separately - if that's *also* stagnant, that's a different, unexplained bug.

**Likely fix shape:** since the 3D rig can't be shown while scoped, the recoil feedback needs to move to the HUD scope overlay itself for that state - a screen shake / reticle kick on `_draw_scope_reticle()` (see bug #5 below, same function) driven by the same `_recoil_kick` state as #1. Worth designing #1 and this together rather than as two unrelated reticle changes, since they're the same underlying need (recoil needs a 2D expression when the 3D rig is what's normally showing it, and isn't right now).

### 7. Lighting/material "stripes" everywhere, moving under weapon/hand motion

**New, found live after the migration to this repo (2026-08-07), not investigated for a fix, but the mechanism is understood.** The user's own words: "get rid of the stripes and fix the lighting... every time I move my gun and hands have moving stripe's reflection... don't know if it's caused by the lighting or the reflection or all the objects and the environments having that ugly stripe." Confirmed visually via a live screenshot in this repo - the red cover boxes in the default arena view show an obvious diagonal candy-stripe pattern, and it's the same material system the weapons/hands use, so it reads everywhere consistently, exactly as the user describes.

**Root cause, found by reading the shader, not guessed:** `shaders/nuclear_pbr.gdshader` (used by the `NuclearMaterials` factory - `metal()`, `polymer()`, `painted_metal()`, `emissive()` - which is what every weapon, hand, and most of the arena's cover geometry is built from) fakes surface detail with **no textures at all**, by design (see the shader's own header comment - the project ships zero imported art). It does this with a sum of four sine waves (`BAND_A`..`BAND_D`, `relief()`, lines 38-93) that perturbs the **shading normal** (line 114, `perturbed = normalize(shading_normal - (tangent * slope.x + bitangent * slope.y) * normal_strength * 0.06)`), not just the albedo. A periodic (sine-based) normal perturbation, combined with `SPECULAR = 0.5` and the engine's real sky/probe reflections (deliberately turned on - see the shader header, "sky reflections and shadows do the work, exactly as they would for an imported metal-roughness material"), produces a periodic specular response: bands of highlight that sweep across the surface as the view angle changes. That's mechanically exactly "moving stripes" - worst on the weapons/hands specifically because they're close to the camera (so the period is large relative to the screen, reading as broad visible bands rather than fine texture) and move constantly (recoil, ADS, sway - all of it sweeps the specular bands visibly), but present on every `nuclear_pbr`-shaded surface, matching "the objects and the environments" too.

This is very likely why the shader comment at line 38 says "so the pattern never resolves into a visible grid at any viewing distance" - the *grid* doesn't resolve, but each individual sine band still reads as a directional stripe under specular/reflection response, which is a different failure mode the original design didn't account for (it was reasoning about the albedo/diffuse read, not the specular one).

**Not a small-number tweak** - this is the core visual-detail technique for every unclothed hard-surface material in the game (the "zero imported art" constraint means there's no texture-based alternative sitting nearby to fall back to), so a real fix means either: damping how much the sine relief is allowed to affect `NORMAL` specifically while leaving its (apparently fine, undisputed) contribution to `ALBEDO`/`AO`/roughness alone (the params are already separately exposed - `detail_strength` for albedo, `normal_strength` for the normal - so a first, cheap experiment is just turning `normal_strength` down hard or to 0 and seeing whether the "cast surface" relief look survives on albedo-only); or replacing the periodic sine relief with something that perturbs the normal non-periodically (the file already has `value_noise()`/`hash13()` on hand, currently used only for the grime layer - reusing that for the normal instead of/alongside the sine bands is the obvious next thing to try, at the cost this file's own comment flags: noise needs extra samples per fragment that the sine sum was specifically chosen to avoid on a 120 Hz mobile target, so watch the frame-rate cost); or something else the next session's own judgment lands on. This is real material/shader design work with a genuine "will it still look intentional and not flat/cheap" visual-quality tradeoff - route it through `frontend-opus`, and verify by actually moving the camera/weapon in a live screenshot sequence (a single static screenshot won't show the "moving" complaint at all), not just a still render.

## A testing-methodology trap that already cost real time once - read before you conclude anything "doesn't work"

`game_eval`'s `await get_tree().process_frame` does **not** reliably step `Node._process()` the way a real running frame does. A repeated `set-value-then-await`-loop pattern intended to let `_process()`'s own per-frame lerps converge over many frames consistently produced *zero* visible change last session - both for forcing a normal weapon into ADS and for the shield's pitch - even after 40 loop iterations. It looked exactly like "the pose code doesn't work."

**What actually works**: directly compute and assign the final, converged target transform in the `game_eval` call (bypassing the lerp/animation entirely - i.e. simulate what several seconds of `_process()` *should* produce, by hand, in one shot), then `get_tree().paused = true` before the screenshot. Example, proven to work:
```gdscript
var d = get_node('/root/RiftlineArena/Actor_host')
var anchor = d._ads_weapon_anchor()
d._weapon_root.position = anchor
d._weapon_rig.rotation = Vector3.ZERO
d.ads_progress = 1.0
d._aiming = true
get_tree().paused = true
```
This is fast and reliable for checking *composition* (does the final pose look right), but it is **not** a substitute for watching the real, input-driven, `_process()`-driven transition happen - which is exactly the gap flagged in bug #6 above. If you need to verify the live transition (not just the end state), you'll need a different approach than either of the above - e.g. driving real input through `game_manage(op="input_action")` rather than poking `Duelist` fields directly, since the live simulation loop resets fields like `_aiming` from real input each tick and fights direct field pokes.
